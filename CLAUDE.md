# CLAUDE.md

Guidance for working on DProcess. See `README.md` for the project overview and usage.

## Commands

- `make check` - everything below plus the spec/types drift check (run before every commit)
- `make test` - `go vet ./...` and `go test ./...`
- `make web-test` - frontend typecheck and vitest
- `make gen-api` - regenerate `web/src/api/schema.d.ts` from `api/openapi.yaml`
- `make run` - start the server (`./dprocess.db`, `127.0.0.1:8080`)
- `make dev-web` - Vite dev server, proxies `/api` to `127.0.0.1:8080`
- `make build` - build the web UI, then `./dprocess` with the UI embedded
- `make clean` - remove binary and DB files

## Domain rules

- Hierarchy: Project → Epic → Story.
- Epic states: `draft, review, ready, finished, cancelled`.
- Story states: `draft, review, design, implementation, ready_for_testing, testing, pr_review, finished, cancelled`.
- A story may depend only on stories in the **same project**; reject self-dependencies and cycles.
- Stories should be estimated at ≤400 LOC. This is **warn-only**: accept larger estimates and return a `warnings` entry (`estimate_exceeds_400_loc`), never reject.
- Stories carry a list of GitHub **pull request links** (`story_pull_requests`, migration `0003`): only canonical `https://github.com/{owner}/{repo}/pull/{n}` URLs, validated by `service.ParsePullRequestURL` (shares `parseGitHubURL` with issues). The list is part of the story, so it freezes with finished/cancelled stories (`store.AddPullRequest`/`RemovePullRequest` return `ErrStoryLocked`) - unlike tags, comments and issue links, which stay open. Deleting a story cascades to its links.
- Projects may carry a GitHub **repository link** (`projects.github_repo_url`, migration `0007`, NULL = none, API `""`): only canonical `https://github.com/{owner}/{repo}`, validated by `service.ParseRepoURL` (trims, strips one trailing slash and one `.git`, lower-cases; the host `github.com` is matched case-insensitively, also by `ParseIssueURL`/`ParsePullRequestURL` via `parseGitHubURL`; 422 `service.ErrInvalidRepoURL`). PATCH with `""`/whitespace clears it, `null`/absent leaves it; validation happens in the handler before any write. Issue and pull request responses carry `warnings` (never null); `repo_mismatch` when the project has a link and the item's `github_repo` differs (`service.RepoMismatchWarning`, filled by the API layer on every read, never rejects). No uniqueness across projects.
- GitHub issues are a **separate entity** (only canonical github.com issue URLs are accepted) that stores references to issues living on GitHub (optionally linked to a story). The server makes no GitHub API calls unless the optional read-only status sync is enabled.
- **Epic transition rules are final** (specified by the user): forward only `draft -> review -> ready -> finished`; `cancelled` from draft/review/ready; `finished` and `cancelled` are final. Finishing needs all stories finished or cancelled and at least one finished. Cancelling cancels every story that is not already finished/cancelled (finished stories are kept) with history rows, atomically. Finished/cancelled epics accept no new stories (`store.ErrEpicClosed`, 409). The rules live in `service.EpicTransitionEffects` (pure, table-tested) and run inside the `store.TransitionEpic` transaction via an `EpicPolicy` callback.
- **Story transition rules are final** (specified by the user): initial `draft`; forward `draft -> review -> design -> implementation -> ready_for_testing -> testing -> pr_review -> finished`; backward only `implementation -> design`, `ready_for_testing -> implementation`, `ready_for_testing -> design`, `testing -> implementation`, `testing -> design`, `pr_review -> design` (review failed); `cancelled` from any state except `finished`; `finished`/`cancelled` final. Gates: move to `review` needs the epic in review or ready; move to `design` (and implementation/ready_for_testing/testing/pr_review, which are only reachable via design) needs the epic ready; move to `finished` needs every dependency (the stories it depends on) `finished` - cancelled dependencies block it. The table is in `internal/workflow`; the data-dependent rules are in `service.StoryTransitionCheck` (pure, table-tested) and run inside the `store.TransitionStory` transaction via a `StoryPolicy` callback.
- **Adding a story state needs a migration that rebuilds `stories`** (SQLite cannot alter a CHECK; see `0005_story_pr_review.sql` and `0006_story_ready_for_testing.sql`). `store.migrate` therefore runs migrations on one pinned connection with `foreign_keys` off (a table drop would otherwise cascade into dependencies, pull requests and issues) and runs `foreign_key_check` before each commit. `state_history` is never rewritten: rows from before a rule change (e.g. `testing -> finished`, `implementation -> testing`) stay as they were.
- **Finished and cancelled stories are frozen** (specified by the user): `PATCH` and adding/removing dependencies *of* such a story return 409 (`store.ErrStoryLocked`); a finished story cannot be deleted, a cancelled one can (still 409 while others depend on it). Exception by design: a live story may remove a dependency on a cancelled story (that is how it escapes one); pointing a live story at a finished/cancelled story is allowed. Tags, comments and issue links are deliberately NOT frozen. The checks are atomic SQL/transactions in `store` (`UpdateStory`, `AddDependency`, `RemoveDependency`, `DeleteStory`).
- **Still unspecified, deliberately not enforced:** cancelling an epic can leave live stories in other epics depending on newly cancelled stories (they must remove the dependency before finishing - allowed).

## Architecture decisions

- Go single binary; REST under `/api/v1`; the React + TypeScript SPA (Vite, in `web/`) will be embedded with `go:embed web/dist`.
- SQLite via `modernc.org/sqlite` (pure Go, no cgo). Connection uses WAL, `foreign_keys(1)`, `busy_timeout`, and `SetMaxOpenConns(1)`. Don't switch to a cgo driver.
- Layering: `store` (SQL) → `service` (business rules) → `api` (HTTP). Simple CRUD without rules may go api → store directly (projects does); add `internal/service` when rules appear (transitions, dependency validation). Keep the state machine isolated in `internal/workflow`.
- No authentication in v1. Transitions record an optional free-text `actor`.
- State changes happen only through `POST .../transition`, never through PATCH. Each transition writes a `state_history` row in the same transaction.
- Deleting a parent that has children is rejected with 409 (`store.ErrInUse`); cancelling is the preferred way to retire things.

## Frontend

- `web/`: Vite + React + TypeScript, React Router, TanStack Query, `openapi-fetch`. All server calls go through `web/src/api/client.ts` (`api` typed from the generated `schema.d.ts`; `unwrap` throws `ApiError` carrying the server's problem document).
- **`api/openapi.yaml` is the contract.** When an endpoint or field changes, update the spec in the same change and run `make gen-api`; `make check-api` fails if the committed types are stale. The spec is hand-written; keep descriptions with a `:` quoted, or the YAML breaks.
- TypeScript is pinned to 5.x on purpose: `openapi-typescript` needs the TS 5 compiler API and crashes on TS 7.
- `web/embed.go` embeds `web/dist` (`//go:embed all:dist`). `web/dist/.gitkeep` is committed so Go compiles before the UI is built; the Vite config re-creates it after each build because Vite empties `dist/`. Never commit other `dist/` files.
- The server (`internal/api/ui.go`) serves the UI at `/` with fallback to `index.html` for extension-less paths; unknown `/api/` paths return a JSON 404, never HTML.
- Frontend tests mock `globalThis.fetch` (`vi.stubGlobal`). Use `mockApi({path: body | Response | fn})` and the `epic()`/`story()` builders from `web/src/test/fixtures.ts`; see `web/src/pages/ProjectPage.test.tsx`. `make check` runs them.
- Routes: `/` (landing: project search by exact name, recently visited projects, new-project form), `/projects` (all projects), `/projects/:projectId` (overview: epic list + story board), `/epics/:epicId` (epic: stories, state history, state-change panel), `/stories/:storyId` (story: fields, state-change panel, dependencies, history). The overview loads a project's epics and stories once and filters in the browser; filters live in the URL (`?epic=&assignee=&tag=`, parsed by `lib/board.ts`, which ignores values that match nothing). Keep grouping/filtering logic in `lib/board.ts` (pure, unit-tested) and rendering in `components/`.
- Workflow rules are enforced by the server only; the UI never re-implements them. `TransitionPanel` offers exactly the epic's `allowed_transitions`, sends `{to, reason}` and shows the server's problem `detail` verbatim when a move is refused (e.g. finishing names the unfinished stories). The one UI-side computation is the cancel confirmation's preview of which stories will be cancelled (not finished/cancelled), which is informational: the server's answer is authoritative and the page refetches afterwards. Story pages should follow the same pattern.
- Forms (`EpicForm`, `StoryForm`) create when given a parent id and edit when given the record; they own their mutation, show the server's problem `detail` inside the form (and dismiss it as soon as a field is edited), and invalidate by key prefix. Client-side checks are limited to what the server cannot see: the estimate must parse as a whole number, and the live "over 400 lines" advisory (`MAX_STORY_LOC` in `lib/forms.ts`, deliberately the same number as the server's; the server never rejects big estimates). Everything else (blank names, negative estimates, frozen stories, closed epics) is the server's call and its message is shown. Finished and cancelled stories are read-only in the UI (`isTerminal`), no Edit button; the server enforces it too. Reuse `StoryForm` for the story detail page.
- `StatePanel` is the one state-change control for epics and stories (`TransitionPanel` and `StoryTransitionPanel` are thin wrappers that supply the endpoint, the refresh and the cancel preview). Backward moves are labelled "Move back to ..." (the server lists them in `allowed_transitions`; the UI only decides the label by stage order). Cancelling is final, so both ask first; the story's confirmation lists the live stories that depend on it (they cannot finish until the dependency is removed).
- `DependencySection` (story page): lists both directions, removes any dependency of a live story (a cancelled one is flagged: per the rules it blocks finishing), and adds through a picker whose candidates come from `lib/dependencies.ts` (same project only; not the story itself, its dependencies or its direct dependents, which would be an obvious cycle; longer cycles are the server's to refuse, and its message is shown). A dependency change refreshes every cached story page (`["story"]` prefix) because both ends change. Finished and cancelled stories show the lists read-only, with no picker and no project data requested.
- Tags and comments (`TagEditor`, `CommentThread`) work on both epics and stories, in every state: the server never freezes them, so the UI never does either (finished/cancelled stories are read-only for their fields and dependencies, not for tags and comments). The server normalizes and validates tags; the UI sends the trimmed text and shows the server's message. Tag chips are links to `/projects/:id?tag=...`, the board's existing tag filter (chips inside the epic cards on the project page stay plain text, since a link cannot sit inside the card's button). The comment author name lives in localStorage (`dprocess.author`, `lib/author.ts`, never throws). A tag change refreshes the story, its epic and its project; comments are fetched under `[kind, id, "comments"]`.
- Issues and pull requests: `IssuesPage` (`/projects/:id/issues`, the story filter lives in `?story=ID|none`) and `IssueForm` manage a project's issue references; `PullRequestSection` and `StoryIssues` sit on the story page. The asymmetry is deliberate and comes from the server's rules: pull request links are part of the story and freeze with it (read-only UI on finished/cancelled stories), issue links do not (linking/unlinking stays open). URL validation (only canonical `https://github.com/{owner}/{repo}/issues|pull/{n}`) is the server's alone; the forms send the text as typed (no `type=url`, which would hide the server's message behind the browser's) and show its `detail`. GitHub links use `target="_blank" rel="noopener noreferrer"`. Issue changes refresh `["project", id]` and every `["story"]` page (the story page lists its issues).
- React Query keys: `["project", id]` prefix covers a project's data (`...,"epics"`, `...,"stories"`); `["epic", id]` prefix covers an epic's (`...,"stories"`, `...,"history"`); `["story", id]` covers a story's (`...,"history"`). After a mutation invalidate by prefix (an epic transition invalidates the epic and its project, a story transition or edit invalidates the story, its epic (progress) and its project (board)).
- Project repo link and `repo_mismatch` badge (story 79): `ProjectRepoForm` on `ProjectPage` (between description and the Issues link; `<form aria-label="GitHub repository">`, own Save button, no read-only/edit switch). Text is sent as typed (empty or whitespace clears it, no confirmation, no `type=url`); Save is disabled while the trimmed input equals the saved value or the request is pending; the server's `detail` is shown in `role="alert"` and dismissed on edit; after success a "Saved" text (not `<output>`, not an alert) shows and the input takes the server's canonical value; no optimistic update. The repo is shown as an `owner/repo` link (`repoLabel` in `lib/github.ts`, `target="_blank" rel="noopener noreferrer"`). A successful save invalidates `["project", id]`, `["projects"]` and the `["story"]` prefix (warnings of cached issues and pull requests change); a refused one invalidates nothing. `RepoWarningBadge` (className `badge warn`, text "other repo", title and aria-label from `repoWarningMessage`) sits beside the links in `PullRequestSection`, `StoryIssues` and the `IssuesPage` cards; the UI never recomputes the mismatch and unknown warning codes show nothing.
- "Recently visited projects" is browser-only state in localStorage (`dprocess.recentProjects`, `[{id, name, visitedAt}]`, newest first, max 10), owned by `lib/recent.ts`, which must never throw (storage can be blocked, full or corrupt). `ProjectPage` records a visit once the project has loaded; the landing page shows the server's current name for each entry and drops/prunes deleted projects. There is deliberately no server-side visit tracking.
- Test setup (`src/test/setup.ts`) clears localStorage and restores mocks after every test. Do not use an `<output>` element as a test probe: it has the implicit ARIA role `status`, which the pages also use.
- Verify layout changes in a real browser, not only with vitest: build with `make web`, run the server, and screenshot with `google-chrome --headless=new --no-sandbox --virtual-time-budget=6000 --screenshot=out.png <url>`.

## Skills

- `plugins/dprocess/` is a Claude Code plugin (marketplace manifest in `.claude-plugin/marketplace.json`; skills are invoked as `/dprocess:<skill>`). Its skills work on a story in stages, each moving it one step on the server (URL: `DPROCESS_URL`, else the one saved by the `init` skill in `~/.config/dprocess/config.json`, else `http://127.0.0.1:8080`): `review-story` (draft -> review, interviewer and interviewee), `design-story` (review -> design; a dev, a tester and a requirements engineer write the tests first on `scratch/storyN-design`), `implement-story` (design -> implementation -> ready_for_testing; renames that branch to `scratch/storyN`; the dev implements in a worktree from which the test files are removed and the tester answers its questions). Testing, the pull request and the merge have no skill yet. The `init` skill (`/dprocess:init`) asks for the server URL, verifies `GET /api/v1/health` and saves it with `skills/init/scripts/dpinit.py`; `dpstory.py` reads the same file inline (skills must not import from each other, so keep the config path and precedence in both in step). Its helper `skills/implement-story/scripts/dpstory.py` (also used by the other skills for `find`) is the way implement-story changes status; `design-story` and `review-story` have their own small helpers. Skills must live under `plugins/dprocess/skills/<name>/` (a plugin's skills are one level deep; Claude Code does not scan nested folders in `.claude/skills`), reference their own files through `${CLAUDE_SKILL_DIR}`, run scripts through their interpreter, and use nothing outside the plugin folder (an installed plugin is copied to a cache). Bump `version` in `plugins/dprocess/.claude-plugin/plugin.json` when the plugin changes, and check it with `claude plugin validate ./plugins/dprocess` and `claude plugin validate .`. Keep the skill in step with the workflow rules documented here.

## Conventions

- Schema changes: add a new numbered file in `internal/store/migrations/` (e.g. `0002_*.sql`); never edit an applied migration. Migrations are embedded and run in order at startup, each in a transaction.
- Errors: use `writeError` (RFC 7807-style `application/problem+json`). Map store sentinel errors in `storeError`: not found → 404, in use / illegal transition / dependency cycle → 409, validation → 422, bad JSON or unknown fields → 400.
- JSON bodies are decoded with `DisallowUnknownFields`; PATCH inputs use pointer fields (nil = unchanged).
- Timestamps are stored as UTC ISO-8601 text.
- Routing uses Go 1.22+ `net/http` patterns (`"GET /api/v1/projects/{id}"`), not a third-party router.
- Tests: use real SQLite in a `t.TempDir()` file (see `newTestServer` in `internal/api/projects_test.go`), not mocks. Cover new endpoints with API tests and rules with table tests.
- Keep each story/change small (≤400 LOC where feasible).

## Roadmap

Done: scaffold + migrations + health; projects CRUD; epics CRUD + `internal/workflow` + epic transition endpoint + history (`store.transition` is shared with stories).
Also done: stories CRUD, transitions, history, LOC warning (`service.StoryWarnings`). A story's epic cannot be changed after creation; deleting a story that others depend on returns 409.
Also done: story dependencies. Their invariants (same project, no self-dependency, no cycle via a recursive CTE) live in `store.AddDependency` rather than `service` because the check and insert must share one transaction.
Also done: tags, comments, GitHub issue references. Tag rules live in `service.NormalizeTag`; issue URL rules in `service.ParseIssueURL` (only `https://github.com/{owner}/{repo}/issues/{n}` is accepted, stored canonical/lower-case, unique per project via migration `0002`).
